# Ceph 2019 年度社区进展报告

## 一、全年技术演进概述

2019年是Ceph发展历程中的重要转折年。年初，社区完成了 **Nautilus（14.x）** 版本的开发冲刺并于3月正式发布，这是继 Mimic 之后的又一个长期支持版本。与此同时，下一个主版本 **Octopus** 的规划工作也在年内全面展开。

全年技术演进呈现出以下几条主线：

- **新一代 OSD 引擎**：Crimson/SeaStor 项目从概念验证走向早期实现，每周例会持续推进
- **编排层统一**：Orchestrator 抽象层逐步成熟，SSH、Ansible、Rook、DepSea 等多后端并行推进
- **存储引擎优化**：BlueStore 持续调优，RocksDB 分片、缓存策略、压缩等方向均有突破
- **云原生融合**：Rook 1.0 发布，Ceph 与 Kubernetes 的集成进入生产就绪阶段
- **Python 3迁移**：全年持续推进 Python 2.7 → Python 3 的代码迁移工作

---

## 二、重大里程碑

### 2.1 Nautilus 正式发布

Nautilus（v14.2.x）是2019年最重要的里程碑。根据 [2019-02-25 Orchestration Meeting](/posts/2019/2019-02-25_-_-_Ceph_Orchestration_Meeting)) 和 [2019-03-20 Testing Meeting](/posts/2019/2019-03-20_-_-_Ceph_Testing_meeting)) 的记录，Nautilus 在发布前经历了多个 RC 版本的密集测试，包括 ARM 构建、Debian 构建、NFS Ganesha 软件包构建等。

Nautilus 的主要新特性包括：
- Messenger v2 协议（加密通信）
- Dashboard 重大改进
- Orchestrator 框架初步集成
- BlueStore 性能优化
- Monitor 选举策略改进

### 2.2 Rook 1.0 发布

根据 [2019-04-29 Orchestration Meeting](/posts/2019/2019-04-29_-_-_Ceph_Orchestration_Meeting)) 和 [2019-05-13Orchestration Meeting](/posts/2019/2019-05-13_-_-_Ceph_Orchestration_Meeting)) 的记录，Rook 1.0.0 于2019年5月正式发布，随后迅速推出了修复升级兼容性问题的 1.0.1 版本。Rook 1.0 的发布标志着 Ceph on Kubernetes 进入生产就绪阶段，新网站同步上线。

### 2.3 Crimson/SeaStor 早期实现

根据 [2019-04-02 Crimson Meeting](/posts/2019/2019-04-02_-_-_Crimson_SeaStor_OSD_Weekly_Meeting)) 的记录，Crimson OSD 在4月完成了初步性能测试，4K 随机读取相比经典 OSD 提升约 50%-60%。[2019-06-04 Crimson Meeting](/posts/2019/2019-06-04_-_-_Crimson_SeaStor_OSD_Weekly_Meeting)) 记录了 pering 功能的合并，标志着 Crimson 可以启动多个 OSD 并执行基本操作。

## 三、核心组件年度进展

### 3.1 Crimson/SeaStor OSD

Crimson 项目在2019年从理论走向实践，全年保持每周例会节奏，是年度技术投入最密集的方向之一。

**架构设计**：根据 [2019-01-29 Crimson Meeting](/posts/2019/2019-01-29_-_-_Crimson_SeaStor_OSD_Meeting)) 和 [2019-02-19 Crimson Meeting](/posts/2019/2019-02-19_-_-_Crimson_SeaStor_OSD_Weekly_Meeting)) 的讨论，团队围绕以下核心问题展开设计：
- 基于 Seastar 框架的无锁异步架构
- PG 状态机（FSM）的最小化实现
- 新的消息帧格式与加密协议
- 内存存储与恢复机制

**性能测试**：[2019-03-26 Crimson Meeting](/posts/2019/2019-03-26_-_-_Crimson_SeaStor_OSD_Weekly_Meeting)) 开始系统性地使用 `perf stat` 工具对比 Crimson 与经典 OSD 的性能，发现 CPU 前端存在瓶颈，指令缓存命中率是关键优化方向。

**关键里程碑**：
- 1月：PG 持久化、心跳支持、消息传递框架初步实现
- 2月：Recovery State Machine 最小实现，v2 协议开发启动
- 3月：FSM PR 审查，PG 状态上报给 Manager
- 4月：Crimson 与经典 OSD 互操作性测试，性能提升约 50-60%
- 5月：异常处理机制讨论，对象上下文缓存优化
- 6月：Pering 功能合并，复制支持开发启动，对象类支持规划

**技术挑战**：根据 [2019-05-14 Crimson Meeting](/posts/2019/2019-05-14_-_-_Crimson_SeaStor_OSD_Weekly_Meeting)) 的讨论，团队面临的主要挑战包括对象上下文缓存的双重缓存问题、持久内存集成、消息批处理机制优化等。

### 3.2 BlueStore

BlueStore 在2019年持续进行性能调优，多个重要 PR 在全年陆续合并。

根据 [2019-02-28 Performance Meeting](/posts/2019/2019-02-28_-_-_Ceph_Performance_meeting)) 的讨论，团队发现 BlueStore 存在双重缓存问题（Block Cache 和 BlueStore 自身缓存），并讨论了针对 SD 场景调整默认缓存大小的必要性。

[2019-04-18 Performance Meeting](/posts/2019/2019-04-18_-_-_Ceph_Performance_meeting)) 记录了 Adam 对 RocksDB 列族分割的测试，发现合理分割列族可带来最高 29% 的性能提升。

[2019-06-20 Performance Meeting](/posts/2019/2019-06-20_-_-_Ceph_Performance_Meeting)) 讨论了 PG 映射缓存（Peachy 映射缓存）的合并，该特性显著提升了性能，以及对象创建操作优化（跳过 BlueStore 中的冗余查找）。

主要进展：
- RocksDB 列族优化，写放大率降低
- BlueStore 缓存策略改进，引入 Priority Cache Manager
- 新位图分配器开发
- 自动调优（Auto-tuning）框架推进
- 支持 discard 操作以优化 SD 空间回收

### 3.3 RGW（RADOS Gateway）

RGW 在2019年有两个重要的技术分享：[2019-04-25 RGW Request Workflow](/posts/2019/2019-04-25_-_-_Ceph_Code_Walkthrough_-_RGW_Request_Workflow)) 和 [2019-05-24 RGW Multisite Replication](/posts/2019/2019-05-24_-_-_Ceph_Code_Walkthrough_-_RGW_Multisite_Replication))，系统性地介绍了 RGW 子系统架构和多站点复制机制。

**多站点复制**：[2019-05-24 代码走查](/posts/2019/2019-05-24_-_-_Ceph_Code_Walkthrough_-_RGW_Multisite_Replication)) 详细介绍了基于日志的复制架构，包括元数据日志、桶索引日志、数据更改日志三种日志类型，以及基于协同程序（co-routines）的并发同步框架。

**性能优化**：根据 [2019-03-28 Performance Meeting](/posts/2019/2019-03-28_-_-_Ceph_Performance_meeting)) 的讨论，RGW 的主要优化方向包括：
- Beast 前端的异步重构
- QoS 在多站点环境下的应用
- 减少线程数量以降低内存消耗和上下文切换
- 无序存储桶列表 API（提升列表性能）

**接口改进**：[2019-06-19 Orchestration Meeting](/posts/2019/2019-06-19_-_-_Ceph_Orchestration_meeting)) 讨论了 RGW 服务接口的重构，将服务器管理、存储桶组管理和 RGW 结构管理分离，并讨论了与 Orchestrator 的集成方式。

### 3.4 Orchestrator框架

Orchestrator 是2019年社区投入最多的工程方向之一，全年保持每周例会。

**架构演进**：根据 [2019-02-11 Orchestration Meeting](/posts/2019/2019-02-11_-_-_Ceph_Orchestration_Meeting)) 的记录，Orchestrator 框架在年初确立了核心设计原则：统一抽象接口，支持 SSH、Ansible、Rook、DeepSea 等多种后端实现。

**主要后端进展**：
- **SSH Orchestrator**：全年持续开发，支持 TLS 双向认证，实现主机管理、OSD 部署等核心功能
- **Rook Orchestrator**：与 Rook 1.0 同步演进，支持 Kubernetes 原生部署
- **DeepSea Orchestrator**：针对 SUSE 平台的实现，全年持续完善
- **Ansible Orchestrator**：基于 Ansible Runner Service，支持 TLS

**关键技术决策**：根据 [2019-03-27 Orchestration Meeting](/posts/2019/2019-03-27_-_-_Ceph_Orchestration_Meeting)) 的讨论，团队确立了 Orchestrator 模块版本兼容性检查机制，以解决 Ceph 版本与外部 Orchestrator 版本不匹配的问题。

[2019-06-19 Container Hudle](/posts/2019/2019-06-19_-_-_Container_Huddle_-_DeviceSet_discussion)) 专门讨论了基于 PVC 的 OSD 设计（Storage Class Device Set），这是 Rook 在 Kubernetes 动态存储场景下的重要架构改进。

### 3.5 Dashboard

Dashboard 在2019年与 Orchestrator 深度集成，成为统一管理入口。根据 [2019-06-03 Orchestration Meeting](/posts/2019/2019-06-03_-_-_Ceph_Orchestration_Meeting)) 的讨论，Dashboard 将主要关注与 Orchestrator 的集成，提供集群管理的图形化界面。

### 3.6 CephFS

根据 [2019-06-05 Developer Monthly](2019-06-05_-_Ceph_Developer_Monthly_part_1) 的讨论，CephFS 在2019年的主要进展包括：
- 快照管理功能增强，支持基于子目录的快照计划和保留策略
- 灾难恢复模式改进
- MDS 缓存内存限制自动调优

### 3.7 Monitor

根据 [2019-05-01 Developer Meeting](/posts/2019/2019-05-01_-_-_Ceph_Developer_Meeting)) 的讨论，Monitor 在2019年的主要改进方向包括：
- 选举策略优化：基于连接数量、延迟和可靠性的综合评分机制
- 多数据中心场景下的故障处理
- 内存目标设置改进（RocksDB 和 OSD map cache的内存分配）

## 四、性能工程体系建设

2019年，Ceph 社区在性能工程体系建设上投入了大量精力，这在全年的 Performance Meeting 记录中有充分体现。

**CBT（Ceph Benchmarking Tool）改进**：根据 [2019-06-13 Performance Meeting](/posts/2019/2019-06-13_-_-_Ceph_Performance_Meeting)) 的讨论，CBT 新增了客户端端点支持，可用于 Crimson 测试和夜间性能基准测试，并规划了 Ansible 后端、容器化测试、UI 和结果解析等功能。

**持续性能测试**：根据 [2019-06-27 Performance Meeting](/posts/2019/2019-06-27_-_-_Ceph_Performance_Meeting)) 的讨论，团队规划了基于 Jenkins 和 GitHub 集成的持续性能基准测试体系，包括性能回归检测和阈值告警机制。Intel 提供了新的 Officalis 集群（含 TLC 和 QLC 驱动器）用于性能测试。

**关键性能优化**：
- 禁用 apptracker 可带来 20-30% 的性能提升
- PG 映射缓存显著减少重复计算
- 异步消息传递优化（用户空间 IOKit 事件）
- RocksDB 预取和缓冲读取模式优化
- 日志记录从 `dout` 改为 `ldout`/`lttng`，减少字符串开销

## 五、社区生态

### 5.1 Cephalocon Barcelona2019

根据 [2019-05-13 Orchestration Meeting](/posts/2019/2019-05-13_-_-_Ceph_Orchestration_Meeting)) 和 [2019-04-09 Orchestration Meeting](/posts/2019/2019-04-09_-_-_Ceph_Orchestration_Meeting)) 的记录，Cephalocon 2019 在巴塞罗那举行，是年度最重要的社区聚会。会议期间，Orchestrator 团队在 Red Hat 巴塞罗那办公室举行了面对面工作会议，讨论了 Octopus 路线图和 Crimson 宏观模块结构。

### 5.2 KubeCon 参与

根据 [2019-05-13 Orchestration Meeting](/posts/2019/2019-05-13_-_-_Ceph_Orchestration_Meeting)) 的记录，Rook 团队在 KubeCon 上进行了演讲和展示，并在展位上为用户提供技术支持，体现了 Ceph 社区在云原生领域的持续投入。

### 5.3 Red Hat Summit

根据 [2019-05-09 Performance Meeting](/posts/2019/2019-05-09_-_-_Ceph_Performance_meeting)) 的记录，Red Hat Summit 期间社区活动相对减少，许多核心成员参会，体现了 Red Hat 作为 Ceph 最大企业贡献者的重要地位。

### 5.4 OVH 大规模部署实践

根据 [200_Clusters_vs_1_Admin](/posts/2019/200_Clusters_vs_1_Admin_-_Bartosz_Rabiega_OVH)) 的分享，OVH 在2019年已拥有超过 50PB 的 Ceph 存储空间，分布在 210 个集群中，单个管理员可管理超过 200 个集群，展示了 Ceph 在欧洲最大云服务商的大规模生产实践。

### 5.5 Google Summer of Code / Outreachy

根据 [2019-02-06 Testing Weekly](/posts/2019/2019-02-06_-_-_Ceph_Testing_Weekly)) 的记录，社区积极参与 GSoC 和 Outreachy 项目，通过简化申请流程和小规模项目评估来吸引新贡献者。

### 5.6 文档改进

根据 [2019-06-12 DocUBetter Meeting](/posts/2019/2019-06-12_-_-_Ceph_DocUBetter_meeting)) 的记录，社区讨论了设立专职文档承包商角色，职责包括维护上游用户文档、改进新贡献者入职文档、创建技术概述文章等，体现了社区对文档质量的重视。

## 六、工程实践改进

### 6.1 测试体系

根据 [2019-05-29 Testing Meeting](/posts/2019/2019-05-29_-_-_Ceph_Testing_meeting)) 和 [2019-06-12 Testing Weekly](/posts/2019/2019-06-12_-_-_Ceph_Testing_Weekly)) 的讨论，2019年测试体系的主要改进包括：
- 升级/降级测试框架建立，确保点版本间数据兼容性
- Smoke测试持续完善
- 探索 KVM 虚拟化测试环境
- 与 OVH 等云服务商合作扩展测试资源

### 6.2 Python 3 迁移

根据 [2019-02-27 Testing Meeting](/posts/2019/2019-02-27_-_-_Ceph_Testing_meeting)) 的记录，由于 Python 2.7 即将停止支持，社区在 Nautilus 发布后开始系统性地推进 Python 3 迁移工作，包括使用 Alfredo 的补丁使代码仅在 Python 3 上运行。

### 6.3 自动错误修复

根据 [2019-03-07 Developer Meeting](/posts/2019/2019-03-07_-_-_Ceph_Developer_Meeting)) 的讨论，社区讨论了 OSD 自动错误修复机制，包括副本池的自动修复、健康警报级别调整、崩溃记录和媒体错误处理等。

## 七、下一年（2020年）展望

基于2019年的讨论和规划，可以推断2020年（Octopus 版本周期）的主要技术方向：

**1. Octopus 版本发布**：根据 [2019-06-17 Orchestration Meeting](/posts/2019/2019-06-17_-_-_Ceph_Orchestration_Meeting)) 的路线图讨论，Octopus 将重点推进 SSH Orchestrator 成熟、升级测试完善、以及部署自动化功能的深度集成。

**2. Crimson/SeaStor 持续演进**：Crimson 将从早期实现走向功能完整，重点完成复制支持、对象类支持、基于日志的恢复等核心功能，并建立与经典 OSD 的公平性能对比基准。

**3. 云原生深化**：基于 PVC 的 OSD 设计（Storage Class Device Set）将在 Rook 中落地，进一步提升 Ceph 在 Kubernetes 动态存储场景下的能力。

**4. 性能工程体系成熟**：持续性能基准测试体系将与 CI/CD 深度集成，每个 PR 都将附带性能影响数据，形成性能回归防护网。

**5. RGW 多站点增强**：基于2019年的架构讨论，RGW 多站点复制的性能和可靠性将持续改进，QoS 支持将进一步完善。

**6. Dashboard 成为一等公民**：随着 Orchestrator 框架成熟，Dashboard 将成为 Ceph 集群管理的主要入口，提供完整的生命周期管理能力。
