## 演讲概述

本次演讲由来自 Taiso 公司的 Dan 主讲，他同时也是 CERN（欧洲核子研究中心）的访问学者，在 CERN 主导构建了云存储基础设施。演讲围绕"一键式 Ceph"这一愿景展开，介绍了三个实用工具，旨在降低 Ceph 集群的运维门槛，推动 Ceph 向更高程度的自主化（autonomous）运营迈进。

Dan 引用了一位长期用户的评价来点明核心问题："Ceph 的问题在于，要使用它，你必须先理解它。" 这句话精准概括了 Ceph 的现状——功能强大，但学习曲线陡峭。


## 背景：RADOS 中的"自主"基因

Dan 提到一个有趣的细节：RADOS（Reliable Autonomic Distributed Object Store）中的 "A" 代表 "Autonomic"（自主调节），而非 "Autonomous"（自主）。Autonomic 类似于人体的自主神经系统，是一种生物性的自我调节机制；而 Autonomous 则是机械意义上的完全自主运行。Ceph 的目标是从前者进化到后者——一个无需外部干预、能够自我管理的存储系统。Dan 认为目前 Ceph 已经达到约 95% 的"全自动驾驶"水平，本次演讲聚焦于剩余的 5%。


## 主题一：数据持久性计算器（Durability Calculator）

### 问题背景

在设计 Ceph 集群时，选择合适的数据保护策略（3x replication、erasure coding 如 4+2、+1 等）以及 PG 数量，对数据持久性有深远影响。长期以来，"每个 OSD 配置 100 个 PG"这一经验值缺乏严格的数学依据，随着磁盘容量不断增大（从 20TB 到 60TB、100TB），这一问题愈发突出。

### 工具介绍

Dan 开发了一个 **Ceph 数据持久性计算器**（Python 脚本），支持两种模式：
- **Monte Carlo 模拟模式**：随机模拟故障场景，统计数据丢失概率
- **数学解析模式**：基于粒子物理背景推导的理论公式

该工具的灵感来自粒子物理领域的实验与理论相互验证方法。

### 新增功能：降级状态下的持久性评估

应用户需求，工具新增了"维护窗口"场景的计算：当一台 host 下线时，集群的数据持久性会从 11 个 9（平均数据丢失间隔约 28 万年）骤降至约 9 个 9（平均数据丢失间隔约 1500 年）。这意味着维护窗口期间存在真实的风险敞口。

### 关键发现

1. **磁盘容量增大显著降低持久性**：在其他条件不变的情况下，仅将磁盘容量增大，持久性可能从 10 个 9 降至 9 个 9，持久性下降约 4 倍。原因是单盘故障后的 recovery 时间更长，二次故障的概率窗口随之扩大。

2. **增加 PG 数量对持久性的补偿效果有限**：通过增加 PG 数量来对抗大容量磁盘带来的持久性下降，效果并不显著——持久性的主要决定因素仍是磁盘容量，而非 PG 数量。这一结论为调整 PG 配置提供了客观依据。

3. **工具的价值在于个性化计算**：由于 OSD 数量、host 数量、磁盘大小、数据平均大小、recovery 速度等变量均会显著影响结果，没有通用答案，必须针对具体集群场景运行计算器。

该工具已作为 Pull Request 提交至 Ceph 官方 GitHub 仓库的 contrib 目录。


## 主题二：数据平衡与维护脚本

### 问题背景

日常运维操作（扩容、替换节点、调整 tunables）往会触发大规模数据迁移，可能导致集群长时间处于 degraded 状态，甚至需要数周才能完成 rebalancing。运维人员需要一种"刹车"机制，能够暂停、控制乃至撤销数据移动。

### 工具介绍

Dan 在 CERN 时期编写了一个维护脚本，核心逻辑是：
- 将数据"钉"（pin）在当前位置，阻止立即的大规模迁移
- 让 Ceph 内置的后台 balancer 以渐进、可控的方式逐步完成数据均衡
- 效果：将集群从"25% 数据 misplaced"状态在数分钟内恢复至"health OK，0% misplaced"

### PG 分裂场景的意外收获

在 Cephcon 上，其他运维人员反馈该工具同样适用于 **PG splitting** 场景。Dan 以一个实际案例说明：将 PG 数量从约 4000 扩展到 32000~64000，传统方式需要数周，使用该工具仅需约 10 分钟——因为 PG 分裂本身不触发数据移动，后续由 balancer 异步完成数据重分布。

### 新 Balancer 开发计划

Dan 与同事 Brian 正在合作开发新一代 balancer，计划先用 Python 原型验证，再推送至上游。新 balancer 将整合运维人员长期积累的"愿望清单"，进一步提升数据均衡的智能化程度。

该脚本已贡献至 Ceph 官方仓库的 contrib 目录，工具集统一命名为 **Otto**。


## 主题三：CephFS 灾难恢复脚本

### 问题背景

CephFS 文件系统损坏是一种低频但高危的场景。官方文档虽然记录了灾难恢复流程，但步骤繁琐，涉及多个复杂的底层工具（部分工具的维护者已离职），运维人员极易因遗漏某一步骤或参数错误而使情况恶化。

### 工具介绍

Dan 的同事 Mikola 编写了一套结构化的 CephFS 灾难恢复脚本，核心设计原则：
- 每一步执行前进行前置检查（检查文件格式、journal 可读性等）
- 每条命令执行后验证退出状态，确认成功后再进入下一步
- 将专家经验固化为可重复执行的自动化流程

### 重要建议

Dan 强调：**不要等到真正需要时才去了解这个工具**。应提前进行"演练"（rehearsal），熟悉工具的使用方式，确保在紧急情况下能够正确操作。


## Q&A 要点

**问题一：持久性计算模型与传统 RAID 计算的区别**

提问者询问该工具的数学模型与传统 RAID 5 等计算方式的差异。Dan 解释：Ceph 的数据分布机制（基于 CRUSH algorithm）与传统 RAID 有本质区别，例如 recovery 是并行进行的，速度远快于单盘故障恢复。过去曾有两次基于 Markov chain 的建模尝试（包括 Google Summer of Code 项目），但均未完成。该工具是首个针对 Ceph 特性建立完整数学模型的实现。

**问题二：数据迁移时间估算**

提问者希望能在添加/移除 host 时获得准确的时间估算。Dan 坦承目前 Ceph 尚无此功能（仅有进度条显示当前进度），并表示这是他个人愿望清单上的重要功能。他以 Terraform/Nomad 的 `plan` + `apply` 工作流为例，设想 Ceph 能够提前预览 CRUSH map 变更的影响范围，再由运维人员确认执行——这将极大提升运维的可预测性和安全性。


## 总结与展望

本次演讲的核心信息是：Ceph 走向"一键式"自主运营，不是靠一次性的革命性重写，而是靠运维人员将实际痛点转化为工具，持续迭代，逐步将专家经验固化到系统中。三个工具分别对应三个关键维度：

| 工具 | 解决的问题 | 状态 |
|------|--------|------|
| 持久性计算器 | 客观评估数据安全性，指导 PG/replication 配置 | 已提交 PR 至 Ceph contrib |
| 维护/平衡脚本 | 安全可控地执行数据迁移，支持 PG splitting | 已贡献至 Otto 仓库 |
| CephFS 恢复脚本 | 结构化执行灾难恢复，防止人为操作失误 | 已贡献至 Otto 仓库 |

所有工具均托管于 **Otto** 项目仓库，欢迎社区参与测试和完善。
