# Ceph 社区季度进展报告 — 2022 Q1

---

## 1. 本季度重点议题

本季度 Ceph 社区的讨论高度集中在以下几个方向：

**Quincy 版本发布准备**
Quincy 是本季度最核心的主线任务。从特性冻结时间的确认、各组件的回溯（backport）策略，到最终的性能测试验证，贯穿整个季度。详见 [Ceph Orchestrator Meeting 2022-01-11](/VideoSummary/2022/01/11/Ceph_Orchestrator_Meeting_2022-01-11/) 和 [Ceph Performance Meeting 2022-01-13](/VideoSummary/2022/01/17/Ceph_Performance_Meeting_2022-01-13/)。

**Orchestrator 稳定性与功能完善**
cephadm/Orchestrator 模块在本季度经历了密集的 bug 修复和功能补全，涵盖 SSH 超时、离线主机检测、NFS 高可用、服务 CPU/内存限制等多个方向。

**性能回归追踪**
Quincy 与 Pacific 的性能对比测试暴露了多处回归，尤其是 BlueStore AVL 分配器相关的写入性能问题，成为性能团队本季度的核心攻关点。

**指标收集架构重**
Ceph Manager 的Prometheus 指标收集在大规模集群下存在严重瓶颈，社区开始讨论将指标导出从 Manager 中解耦的长期方案。详见 [Ceph Developer Monthly 2022-02](/VideoSummary/2022/02/03/Ceph_Developer_Monthly_2022-02-02/)。

## 2. 技术亮点

### Orchestrator / cephadm

- **SSH 超时与离线主机检测**：引入 cephadm 超时参数，设置可配置的默认超时时间（约 20 分钟），超时后触发健康警告。同时探索通过 agent 快速心跳检测替代 SSH 轮询，减少对 SSH 的依赖。详见 [Ceph Orchestrator Meeting 2022-01-25](/VideoSummary/2022/02/01/Ceph_Orchestrator_Meeting_2022-01-25/)。

- **服务 CPU/内存限制**：在服务规范（service spec）中引入 CPU 和内存限制属性，支持对每个服务独立设置资源上限。详见 [Ceph Orchestrator Meeting 2022-01-04](/VideoSummary/2022/01/11/Ceph_Orchestrator_Meeting_2022-01-04/)。

- **NFS 高可用性**：测试验证了 NFS daemon 在节点离线后能够重新调度，恢复时间约 1-2 分钟。同时讨论了多 NFS daemon 共存的端口冲突解决方案，以及通过 agent 加速心跳检测的优化方向。详见 [Ceph Orchestrator Meeting 2022-03-22](/VideoSummary/2022/03/29/Ceph_Orchestrator_Meeting_2022-03-22/)。

- **NFS Manager 模块解耦**：移除 NFS 导出命令对 Orchestration 模块的强依赖，使 Rook 等场景可以在不启用 Orchestrator 的情况下管理 NFS 导出。详见 [Ceph Orchestrator Meeting 2022-02-01](/VideoSummary/2022/02/02/Ceph_Orchestrator_Meeting_2022-02-01/)。

- **外部 Prometheus 支持**：开发新端点，允许外部 Prometheus 实例动态获取 Ceph 集群的监控配置，不再依赖静态配置文件。详见 [Ceph Orchestrator Meeting 2022-03-15](/VideoSummary/2022/03/18/Ceph_Orchestrator_Meeting_2022-03-15/)。

- **升级粒度控制**：实现按主机（per-host）和按 daemon 类型（per-daemon-type）的升级选项，满足大型集群用户对升级过程精细控制的需求。详见 [Ceph Orchestrator Meeting 2022-02-07](/VideoSummary/2022/02/12/Ceph_Orchestrator_Meeting_2022-02-07/)。

### 性能优化

- **BlueStore PG 日志优化**：提出将 PG 日志写入缓冲区的方案，减少对 RocksDB 的写放大依赖，降低 RocksDB 资源消耗。详见 [Ceph Performance Meeting 2022-03-24](/VideoSummary/2022/03/29/Ceph_Performance_Meeting_2022-03-24/)。

- **RocksDB Tombstone 清理**：针对 RGW bucket 列表场景下 RocksDB 因大量 tombstone 导致的性能退化，提出通过 TTL 定期触发 compaction 的解决方案。详见 [Ceph Performance Meeting 2022-01-27](/VideoSummary/2022/02/02/Ceph_Performance_Meeting_2022-01-27/) 和 [Ceph Performance Meeting 2022-03-17](/VideoSummary/2022/03/18/Ceph_Performance_Meeting_2022-03-17/)。

- **Scrub Chunk Size优化**：区分 deep scrub 和 regular的 chunk 大小配置，在优化 scrub 吞吐的同时减少对客户端请求的影响。详见 [Ceph Performance Meeting 2022-01-27](/VideoSummary/2022/02/02/Ceph_Performance_Meeting_2022-01-27/)。

- **Tracing 默认编译**：将 tracing 功能默认编译进 Ceph，虽有轻微性能开销，但显著提升了用户调试便利性。详见 [Ceph Performance Meeting 2022-02-03](/VideoSummary/2022/02/03/Ceph_Performance_Meeting_2022-02-03/)。

- **Primary Balancer 重构**：简化了计算 PG Up Maps 的代码逻辑，相关 PR 已合并。详见 [Ceph Performance Meeting 2022-01-13](/VideoSummary/2022/01/17/Ceph_Performance_Meeting_2022-01-13/)。

- **OpenCAS 缓存集成**：Intel 工程师介绍了 OpenCAS（Linux 块层存储缓存软件）与 Ceph OSD 的集成方案，支持写通、写回等多种缓存模式，可作为 OSD 的加速层。详见 [Ceph Performance Meeting 2022-03](/VideoSummary/2022/03/04/Ceph_Performance_Meeting_2022-03-03/)。

### 指标收集架构

- **Manager 指标瓶颈**：在大型集群中，Ceph Manager 每秒需处理约 50MB 指标数据，成为显著瓶颈。社区提出短期方案（减少导出指标数量）和长期方案（per-node 或 per-daemon 独立 exporter，绕过 Manager 直接推送 Prometheus）。详见 [Ceph Developer Monthly 2022-02-02](/VideoSummary/2022/02/03/Ceph_Developer_Monthly_2022-02-02/)。

## 3. 重要决策与里程碑

**Quincy 特性冻结**
本季度初确认了 Quincy 版本的特性冻结节点，self-adm 二进制文件重构被列为冻结前必须完成的工作。Rook Manager Module 因尚未完成测试，不纳入 Quincy 初始版本。详见 [Ceph Orchestrator Meeting 2022-01-11](/VideoSummary/2022/01/11/Ceph_Orchestrator_Meeting_2022-01-11/)。

**Rook 定位讨论**
社区就 Rook Manager Module 的长期定位进行了深入讨论。核心结论是：Kubernetes 环境下 Rook 的操作模式与 cephadm 存在根本差异，部分 Orchestrator API 对 Rook 并不适用，需要为 Rook 设计独立的 API 或调整文档定位。详见 [Ceph Orchestrator Meeting 2022-02-15](/VideoSummary/2022/02/15/Ceph_Orchestrator_Meeting_2022-02-15/)。

**版本降级策略**
讨论了 minor 版本降级支持的可行性，结论是当前实现存在迁移处理和升级状态等问题，建议在新 major 版本中通过强制标志（force flag）重新实现降级支持，并在 minor 版本发布前进行专项测试。详见 [Ceph Orchestrator Meeting 2022-03-08](/VideoSummary/2022/03/08/Ceph_Orchestrator_Meeting_2022-03-08/)。

**AVL 分配器性能回归确认**
通过二分法定位到 Quincy 中写入性能回归的根因：AVL 分配器的行为变更（First Fit vs Best Fit 模式切换）。团队决定测试回滚该变更的效果，并评估是否在发布前修复。详见 [Ceph Performance Meeting 2022-03-31](/VideoSummary/2022/03/31/Ceph_Performance_Meeting_2022-03-31/)。

**Teuthology 本地化**
决定推进 Teuthology 的容器化本地部署方案，使用 Docker Compose 自动化安装过程，降低外部贡献者的参与门槛。详见 [2022-03-24 Ceph Tech Talk - Running Teuthology Locally](2022-03-24_-Ceph_Tech_Talk_-_Running_Teuthology_Locally)。

## 4. 社区动态

**团队变动**
Sebastian 于 1 月底离开 Red Hat，Adam 接手 Orchestrator 周会的主持工作。详见 [Ceph Orchestrator Meeting 2022-01-18](/VideoSummary/2022/01/18/Ceph_Orchestrator_Meeting_2022-01-18/)。

**Science Working Group**
科学计算工作组本季度新增了来自 GWDG（管理约 7PB 存储，计划扩容至 19PB+）和 Flatiron Institute（单集群约 30PB）的成员。会议讨论了大规模集群中的 BlueStore corruption、快照性能、元数据瓶颈等实际运维问题，并提及即将举行的 Cephalocon 会议。详见 [Ceph Science Working Group 2022-01-26](/VideoSummary/2022/02/01/Ceph_Science_Working_Group_2022-01-26/)。

**Cephadm 开发者文档**
社区启动了 cephadm 开发者文档项目，计划覆盖重要数据结构、服务循环机制、Monkey Store 存储格式、Manager 故障转移持久化等内部实现细节，面向开发者而非最终用户。详见 [Ceph Orchestrator Meeting 2022-03-01](/VideoSummary/2022/03/01/Ceph_Orchestrator_Meeting_2022-03-01/)。

**Quincy 性能测试**
性能团队在本季度使用包含 975 个 OSD 的大规模集群进行了 Quincy 版本的系统性能测试，覆盖 RBD、RGW、iSCSI、NBD 等多种工作负载，并引入了新的恢复测试方法（使用独立池和 fio 模拟 OSD 故障恢复）。详见 [Ceph Performance Meeting 2022-01-13](/VideoSummary/2022/01/17/Ceph_Performance_Meeting_2022-01-13/) 和 [Ceph Performance Meeting 2022-01-20](/VideoSummary/2022/01/20/Ceph_Performance_Meeting_2022-01-20/)。

**MClock 配置测试**
计划在 Giba 集群上使用 CBT 对 MClock 的三种配置文件（高客户端 IO、高恢复操作、平衡）进行系统性测试，评估其对 scrubing 和恢复操作的影响。详见 [Ceph Performance Meeting 2022-02-03](/VideoSummary/2022/02/03/Ceph_Performance_Meeting_2022-02-03/)。

## 5. 下季度展望

基于本季度的讨论内容，预计 2022 Q2 将重点推进以下方向：

1. **Quincy 正式发布**：本季度已完成特性冻结和大规模性能测试，Q2 预计将完成最终验证并正式发布 Quincy 版本，同时推进对 Pacific 的backport 工作。

2. **AVL 分配器修复**：BlueStore 写入性能回归问题已定位到 AVL 分配器，Q2 将完成修复验证并决定是否纳入 Quincy 发布版本或作为后续 patch。

3. **cephadm Agent 功能扩展**：本季度已规划了 agent 替代 SSH 的完整功能列表，Q2 将推进 agent 在部署、管理、心跳检测等场景的能力建设，逐步减少对 SSH 的依赖。

4. **指标收集架构演进**：Manager 指标瓶颈的长期解决方案（per-daemon exporter）已完成原型设计讨论，Q2 预计进入实验性实现阶段。

5. **Rook 集成方向明确**：社区已识别 Rook 与 cephadm 的架构差异，Q2 将通过专项会议（含 Dashboard 团队和 Rook 团队）明确 Rook Manager Module 的最终定位和 API 设计方向。

6. **PG 日志优化落地**：将 PG 日志写入缓冲区、减少 RocksDB 依赖的方案已进入讨论阶段，Q2 预计推进具体实现。
